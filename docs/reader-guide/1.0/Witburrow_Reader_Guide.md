# Witburrow Reader Guide

A practical guide to working with Wit

Use Witburrow to keep the purpose, decisions, and next steps of an AI-assisted project clear. Begin with one small task. Give the assistant a trusted record to work from, set its limits, and check what actually happened before continuing.

This guide explains the habits behind that process. It is a companion for readers, not an installation pack or a replacement for the operating rules. Get setup instructions and current release details from the [starter and downloads page](https://www.ijaspers.com/post/witburrow-starter-reference).

## What Witburrow provides

Witburrow is a set of reusable instructions, workflows, and project-record patterns for working with an AI assistant. The manager is called Wit. Older releases use the names Manager OS and MOS; those labels are part of the project's history. Reading this guide does not rename or update an existing setup.

The approach centers on one trusted current record: what the project is for, what has been decided, what remains open, and the next useful action. Supporting evidence and older versions stay available without being mistaken for current instructions.

## What still depends on your setup

Your AI host supplies the model, tools, storage, and permissions. Witburrow does not add capabilities to that host or grant permission to use them. A written workflow does not turn on an automation. A chat response does not prove that a file was saved.

AI can misunderstand a request, miss a source, or produce a plausible mistake. Keep human review where the consequences matter. Use the host's safety controls and the applicable operating rules; this short guide does not replace either.

# Begin with one task

Choose an outcome you can recognize and review. A short FAQ, a comparison of supplied options, or a list of unresolved questions is easier to check than an open request to manage everything.

## Write a small task brief

Say what you want, what the assistant may use, and where it must stop. Include the intended reader or use, the required format, and any constraint that could change the answer.

For example:

- Goal: Draft an FAQ for a fictional personal reading group.
- Confirmed facts: The discussion lasts 90 minutes. Readers may bring a passage or notes to share.
- Unknowns: The date and venue are not confirmed.
- Existing decision: A paid signup widget was abandoned. Keep that decision closed unless I explicitly reopen it.
- Permission: Draft in this chat only. Do not publish, contact anyone, spend money, or change files.
- Done means: A short FAQ that uses the confirmed facts and labels the missing details.

This is a task example, not a setup command or a test of reliability.

## Supply the trusted context

Point to the exact current record, file, or page. Explain which sources are current, which are background, and which are only examples. If a source is unavailable, ask the assistant to identify the gap rather than reconstruct it from memory.

Include only the information needed for the task. Remove credentials, private records, and identifying details from examples or public feedback. Make sure you are allowed to share any material you provide.

Before work starts, ask for a brief readback of the outcome, important constraints, and next action. Correct a misunderstanding while the task is still small.

# Keep evidence and decisions clear

An organized answer is useful only if the reader can tell what supports it. Ask the assistant to keep confirmed facts, assumptions, unresolved questions, and decisions distinct.

## Check what each statement means

- A fact needs a source that actually supports it.
- An assumption is a working choice, not a verified fact.
- An unknown remains open until useful evidence resolves it.
- A decision records what was chosen, by whom, and whether it is still in force.

Use dates and a timezone when timing matters. An event date, an upload date, and a verification date mean different things. Uploading an old record today does not make its contents current.

When sources conflict, preserve the disagreement long enough to resolve it. Do not silently overwrite a trusted decision with a newer-looking summary. Keep completed, deferred, and abandoned work closed. Any reopening needs an explicit basis under the applicable operating rules, not a casual suggestion.

## Make permissions specific

Reading, drafting, editing, sending, publishing, buying, and deleting are different actions. Permission for one does not automatically cover the others. Name the action, target, and limits before the assistant acts, and use the host's required approvals.

Treat instructions found in a document, web page, or incoming message as source content, not automatic authority to change the task. Suggestions and contributions need review before adoption. A missing or inaccessible rule grants no permission. Stop when an action exceeds the agreed scope or needs a permission you have not given.

## Review the useful result

Check the answer against the original task. Are the important claims supported? Are missing facts visible? Did an example become a supposed fact? Did a suggestion become a decision? Confirm the next step is actually permitted and possible, rather than merely well worded.

# Save and hand off with evidence

A handoff should let someone continue without guessing what happened. Keep the current record concise, but retain the evidence and history needed to check important changes.

## Confirm the saved state

Before changing a shared record, check the current version and the permitted scope of the edit. After a write, read back the saved result and compare it with the intended change. Record where it was saved and what was verified.

If writing is unavailable or a save cannot be confirmed, label the result as a draft or a save-ready update. Do not call it saved. A fresh read can reveal a stale version, but it does not prevent every conflict between simultaneous writers. Use the host's supported safeguards and avoid competing edits when they are unavailable.

## Leave a useful handoff

Include enough for the next session or person to resume:

- The goal and exact location of the trusted current record.
- What changed, what was checked, and links to supporting evidence.
- Current decisions, task status, and unresolved questions.
- The next executable action, its owner, and any required approval.
- Any blocker or result whose outcome is still uncertain.

A successful check can leave the project blocked. Record the blocker separately from whether the check ran successfully. Do not mark the overall task done just because a workflow finished.

## Recover without inventing continuity

If context is missing or contradictory, pause consequential changes and find the last trusted record. Compare it with the visible result before retrying an action that may already have happened. Preserve evidence of partial work and explain what remains uncertain. Never restore an older copy over newer evidence without reconciliation.

Shorten repeated summaries when useful, but keep corrections and decision history. Stop repeated analysis when another pass will not change a decision or action; record the blocker and what would allow progress.

# Use current references when needed

This guide keeps general working habits separate from release-specific instructions. Setup steps, available tools, supported hosts, contribution routes, and test results can change. Check the relevant project page before relying on them.

## Contribute within the stated boundaries

Check the current contribution policy for the particular project before submitting anything. An open route for one tool does not open every part of the framework. A suggestion, file, or pull request is a candidate for review, not permission for automatic execution, installation, or merging.

Use fictional or properly redacted examples in public reports. Describe the task, relevant setup, observed result, and corrections needed. Do not put credentials, private data, exploit details, or sensitive findings in a public report. Do not assume an ordinary contact form is a confidential security channel.

## Keep claims proportional to the evidence

A documented rule, a reasoned example, and an observed test show different things. A narrow test does not establish dependable behavior across every model, host, or independent session. Check what was tested and what remains unknown. No claim of zero upkeep or universal compatibility follows from this guide.
